=====================================================================
PROJECT OVERVIEW
=====================================================================
Academic research project (French PFE — end-of-studies project) on
optimizing quantum circuits with genetic algorithms. Goal: take a
target quantum circuit (or unitary), partition it, and evolve a
cheaper/shallower circuit that still reproduces the target's behavior
with high fidelity.

Stack: Qiskit (circuit simulation) + DEAP (evolutionary computation,
NSGA-II / NSGA-III style multi-objective optimization).

The codebase is a research sandbox, not a packaged library: a
progression of standalone Jupyter notebooks and scripts, each an
iteration of the same core pipeline (mono-objective -> multi-objective
-> block-decomposed/scalable). No shared package, no test suite, no
build step.

=====================================================================
REPOSITORY STRUCTURE (reading order / sophistication progression)
=====================================================================
1. AG_mono/
   Mono-objective genetic algorithm: evolve a chromosome (gate
   sequence) approximating a target unitary, optimizing fidelity only.

2. NSGA-II/, NSGA-III/
   Multi-objective versions (fidelity, depth, gate cost) using DEAP's
   NSGA-II/NSGA-III selection.
   NOTE: this checked-out copy DOES contain an NSGA-III/ directory
   (AG_multi_objectifs_NSGA3.ipynb). Flagged for follow-up since this
   fork was reported to be missing the NSGA-III implementation done
   in a prior session — verify whether this notebook is the same
   version, an earlier draft, or something else before assuming it
   needs to be re-added.

3. m1/, m1_bloc_indep/, M1_indicateurs_version/, M1_finale/
   "M1" line of work: adds circuit partitioning into qubit blocks (so
   NSGA-II runs per-block instead of on the whole circuit) plus
   quality indicators (hypervolume, IGD, spread, epsilon).
   M1_finale/ is the most complete/cleaned-up version, with extracted
   .py scripts alongside its notebook.
   -> M1_finale/final_m1_script.py is the canonical, most-maintained
      pipeline implementation (1485 lines).

4. m2_bloc_chevauche/
   "Block overlap" variant: blocks may share qubits at interfaces
   rather than being a strict partition.

5. Final_test/, final_test_AG/, test/
   Later validation/experiment notebooks applying the pipeline to
   specific target circuits (QAOA, MaxCut, W-state, QFT, VQE,
   14/64-qubit cases, etc.), one subdirectory per experiment. These
   are throwaway experiment copies, not a distinct architecture.

Duplicated notebook snapshots (e.g. "code_travaille copy 3.ipynb",
"test3D(1) copy.ipynb") are not divergent components — don't assume
fixes need to be propagated across copies without checking first.

=====================================================================
CORE PIPELINE (M1_finale/final_m1_script.py) — reference implementation
=====================================================================
Entry point: optimise_circuit_pipeline(...)

1. Partitioning
   - build_interaction_graph: qubit-interaction graph weighted by
     2-qubit gate count.
   - louvain_partition: Louvain community detection to split qubits
     into blocks.
   - multilevel_partition: Metis/Kernighan-Lin recursive alternative
     for bounding block size.
   - extract_interblock_gates: captures gates crossing block
     boundaries for later reinjection.

2. Sub-circuit extraction / recomposition
   - extract_subcircuit: pulls a self-contained, locally-reindexed
     circuit per block.
   - recompose_from_blocks: stitches optimized block circuits back
     into a global circuit in original gate order, preserving
     inter-block gates unchanged.

3. Fidelity metric
   - compute_fidelity: operator-overlap fidelity
     |Tr(U_circ . U_target^dagger)| / 2^n.
   - Short-circuits to 1.0 above 15 qubits to avoid dense-matrix
     blowup — this cap is why the pipeline is only exercised on
     small/weakly-connected circuits despite claiming to scale.

4. Intra-block optimization
   - optimise_block_nsga2: DEAP NSGA-II per block, three objectives
     (maximize fidelity, minimize transpiled depth, minimize
     chromosome-length cost).
   - update_rotation_angles: finite-difference local search ("LAS")
     nudging rotation angles after the genetic search converges.

5. Inter-block gate injection (re-adds cross-block entanglement lost
   during block-local optimization)
   - sa_injection: simulated annealing over an energy combining gate
     count, depth, crosstalk, fidelity penalty.
   - stochastic_injection: random trial-and-keep-if-fidelity-improves.
   - fidelity_driven_injection: simpler greedy variant, used as a
     complementary final pass.

6. Compression
   - Hand-rolled passes: cancel_inverse_gates, merge_rotations,
     remove_negligible_rotations (composed in compress_custom).
   - Standard Qiskit PassManager pass (qiskit_opt_pass):
     Optimize1qGates + CommutativeCancellation.

7. Multi-objective quality indicators
   - evaluate_run / compute_hv / spread_delta / compute_spacing /
     compute_epsilon: hypervolume, spread, spacing, epsilon indicator,
     and IGD when a reference Pareto front (P_star) is supplied.
   - Tracked across generations, not just best-fitness.
   - export_all_indicators / plot_moo_history / save_plot /
     plot_convergence / plot_pareto / plot_3d_clusters write PNGs to
     out_figs/ (created on demand).

Later stages depend on earlier ones' output shape (block list,
per-block optimized circuit, kept-injection list) — check
optimise_circuit_pipeline's call sequence before changing an output
type.

Also present: random_weakly_connected_circuit — generates synthetic
test circuits (used by the 30-qubit and 64-qubit runnable examples).

=====================================================================
CONVENTIONS SPECIFIC TO THIS CODEBASE
=====================================================================
- Chromosome encoding: individuals are Python lists of gene tuples
  (gate_name, target_qubit, ctrl_qubit_or_None, angle_or_None). Any
  new gate type added to a gate_pool needs matching branches in every
  build/build_fn closure that turns chromosomes into QuantumCircuits
  (these closures are redefined locally inside each optimisation
  function rather than shared).
- DEAP creator classes (creator.FitnessMulti, creator.Individual) are
  registered guarded by hasattr(creator, ...) checks since DEAP raises
  on re-registration — preserve this guard across notebook re-runs.
- Figures are a primary output, not incidental logging — stdout
  progress prints use emoji status markers (checkmark/cross/money/
  pin-style icons). Keep this pattern when extending a pipeline stage.
- Comments, docstrings, print messages, plot labels, and markdown
  prose are English throughout (originally French, translated in
  full). The two thesis PDFs at the repo root remain in French
  (academic writeups, not code).
- Most heavy computation (chromosome fitness evaluation) is
  parallelized via joblib.Parallel(n_jobs=...) — eval_ind-style
  functions must stay picklable for multiprocessing.

  implemented. No correctness bugs found.

  2. Gene tuple order was [target_qubit, gate, control, angle] (kept
     from the older NSGA-II notebook it was adapted from), inconsistent
     with the (gate_name, target_qubit, ctrl, angle) convention used in
     M1_finale and documented in CLAUDE.md. Reordered to
     [gate, target_qubit, control, angle] in generate_gene,

  3. Removed leftover `pip install qiskit/pylatexenc/matplotlib` cells

  4. parallel_evaluation spawned a fresh joblib worker pool on every

     `with Parallel(n_jobs=-1) as parallel:` block spanning the whole
     run and passes it through, reusing one pool instead of repeatedly
     paying process-pool startup cost.
  Verified after the fixes with the same smoke test: output is

NEXT STEPS — CANDIDATE MOO ALGORITHMS TO ADD
=====================================================================
Beyond NSGA-II/NSGA-III, the following multi-objective algorithms
would fit naturally into the existing per-block optimization slot
(currently optimise_block_nsga2 in M1_finale/final_m1_script.py) and
could be added as interchangeable strategies, similar to how
sa_injection / stochastic_injection / fidelity_driven_injection are
already interchangeable for the injection stage.

1. SMS-EMOA (S-Metric Selection EMOA)
   - Hypervolume-indicator-driven selection instead of crowding
     distance. Directly reuses the project's existing compute_hv
     function as the selection criterion rather than just as a
     post-hoc reporting metric — tightest synergy with code already
     in the repo.
   - Tends to produce better-distributed, higher-quality fronts than
     NSGA-II for 2-3 objectives (fidelity, depth, cost), at higher
     per-generation cost (hypervolume contribution calculation).

2. IBEA (Indicator-Based Evolutionary Algorithm)
   - Generalizes SMS-EMOA to arbitrary indicators; could plug in
     compute_epsilon (already implemented) as the driving indicator
     instead of hypervolume. Good candidate for comparing indicator
     choices against each other using the project's own
     evaluate_run/export_all_indicators reporting.

3. MOEA/D (Decomposition-based MOEA)
   - Decomposes the 3-objective problem (fidelity, depth, cost) into
     scalar subproblems via weight vectors (Tchebycheff or weighted
     sum), each solved cooperatively with neighbor information sharing.
   - pymoo (already a project dependency per requirements notes) ships
     a ready MOEA/D implementation — lowest implementation cost of
     this list if built on pymoo rather than hand-rolled in DEAP.
   - Conceptually maps well onto the block-partition architecture:
     each qubit block could own a distinct region of weight-vector
     space rather than all blocks running identical NSGA-II.

4. SPEA2 (Strength Pareto EA 2)
   - Classic alternative fitness assignment (strength + density via
     k-th nearest neighbor) with an external archive of fixed size.
   - Useful as a baseline comparison against NSGA-II on the same
     3-objective problem to see whether NSGA-II's crowding distance
     is actually the best diversity mechanism for this circuit search
     space, or just the default choice inherited from earlier
     iterations of the project.

5. Multi-Objective Simulated Annealing (MOSA)
   - The project already has single-objective SA for inter-block
     injection (sa_injection, energy = weighted combination of gate
     count, depth, crosstalk, fidelity penalty). A genuinely
     multi-objective SA (Pareto-dominance-based acceptance criterion,
     archive of non-dominated states) could replace that weighted-sum
     energy function and produce a full injection-stage Pareto front
     instead of a single injected solution.
   - Lower implementation lift than the above since it extends
     existing SA machinery (_sa_energy, _sa_rand_move, _sa_generate_pool)
     rather than introducing a new population-based framework.

6. MOPSO (Multi-Objective Particle Swarm Optimization)
   - Different metaheuristic paradigm (swarm, not GA) — worth
     including as a diversity-of-method comparison point in the
     thesis, since all current algorithms (NSGA-II/III, SA variants)
     are either GA- or SA-based.
   - Chromosome encoding (gate_name, target_qubit, ctrl_qubit, angle)
     would need a continuous-relaxation or discrete-PSO adaptation
     before particles can be applied to gate sequences — higher
     implementation cost than the others on this list.

Suggested priority order given existing code reuse:
  MOSA (extends sa_injection) > SMS-EMOA (reuses compute_hv) >
  IBEA (reuses compute_epsilon) > MOEA/D (via pymoo) > SPEA2 > MOPSO.

NEXT STEPS — IMPROVEMENTS FROM RELATED WORK (web research, 2026-08-18)
=====================================================================
Grounded in recent (2024-2026) literature on GA/MOO quantum circuit
optimization, partitioning, and alternatives. Each item names why it
applies to this specific codebase, not just in general.

1. Hyperedge-aware partitioning instead of pairwise Louvain clustering
   - build_interaction_graph/louvain_partition collapse multi-qubit
     gates to pairwise edges and fix block structure via modularity.
   - A 2025 dynamic hypergraph partitioning approach models gates as
     hyperedges (qubit x time nodes) and sweeps block-count K with
     METIS instead of assuming modularity picks the right K.
   - Source: arXiv 2506.09963

2. Cheaper fidelity proxy to replace the hard 15-qubit cutoff
   [DEFERRED -- research is proceeding on a fixed 8-qubit benchmark
   set for now; this item is parked along with the rest of the
   scaling work. See "SCALING — DEFERRED" after Phase 2 below.]
   - compute_fidelity short-circuits to 1.0 above 15 qubits — a
     "Scalable Multi-Objective Genetic Algorithm for Quantum Circuit
     Optimization" paper targets this exact bottleneck via a
     projection-based approximation + structure-aware local metric
     folded directly into NSGA-II, avoiding full dense-unitary builds.
   - Source: nature.com/articles/s41598-026-47674-5 (worth reading in
     full; preprint mirror was paywalled/403 at research time)

3. Classical-shadow / tensor-network fidelity estimation for scale
   [DEFERRED -- same as item 2 above, parked with the rest of the
   scaling work.]
   - Tensor-network-backed classical shadow tomography gives
     sample-efficient fidelity/property estimation without building
     the full 2^n x 2^n operator — would let the pipeline's scaling
     claims actually be tested past 15 qubits instead of stubbed out.
   - Source: arXiv 2209.02093

4. Benchmark mutation operator combinations explicitly
   - GECCO 2025 work found "swap+addition" maximizes fidelity but
     grows depth, while "swap+addition+delete" gives a better
     fidelity/depth balance.
   - optimise_block_nsga2's mutation operators are currently a fixed,
     one-off choice — this gives a citable, testable ablation to run
     per-block and report on.
   - Source: arXiv 2504.06413

5. Formalize the hybrid GA + parameter-refinement split as a named,
   compared variant
   - A companion GECCO 2025 paper separates "hybrid" (GA + rotation-
     parameter subroutine) from "pure" (mutation/crossover only)
     variants, and tests both "build from scratch" and "refine
     existing circuit" starting points.
   - This project already has an ad-hoc version of the hybrid idea
     (update_rotation_angles/LAS after NSGA-II) but has never
     formalized it as a variant to compare against pure-GA — an easy
     controlled experiment to add.
   - Source: arXiv 2504.17561

6. RL + ZX-calculus as a compression-stage alternative
   - An RL agent (PPO + GNN) applying ZX-diagram rewrite rules scales
     to 80 qubits / thousands of gates and beats hand-coded ZX
     simplification strategies; a PyZX-based Qiskit transpiler pass
     exists for integration.
   - compress_custom's hand-rolled inverse-cancellation/rotation-
     merging passes are exactly the category of hand-coded rule this
     method outperforms — could be swapped in, or run as an
     additional final compression pass.
   - Source: arXiv 2312.11597 (Quantum, 2025)

7. Add a noise/crosstalk-aware objective, not just math fidelity
   - Frameworks like CQC (crosstalk-aware compilation) and CCMap
     (coupler-aligned, noise-aware modular compilation; +21.9%
     fidelity / -58.6% compile cost vs baselines in their reported
     results) fold real device error rates and crosstalk into the
     cost function rather than treating fidelity as pure unitary
     overlap.
   - Directly closes a gap this project's own docs already note (no
     noise model, no coupling-map awareness) — could become a 4th
     NSGA-II objective, or a term in the SA injection energy function
     (_sa_energy already has a crosstalk term placeholder to extend).
   - Sources: arXiv 2207.05751, arXiv 2505.09036

8. Noise-weighted partition cuts
   - DisMap/FitCut-style distributed compilation weights partition
     boundaries by qubit error rate/topology, not just gate-crossing
     count, when deciding where to cut.
   - extract_interblock_gates/partitioning currently only minimizes
     cross-block gate count — adding a hardware-error term would make
     block boundaries reflect real device quality, complementing #7.

Suggested priority given effort vs payoff for the thesis (items 2/3
deferred along with the rest of the scaling work, see below):
  #4 and #5 (cheap, purely experimental/ablation, no new deps) >
  #1 (partitioning quality, moderate effort) >
  #7/#8 (adds a genuinely new evaluation dimension — hardware realism
  — but requires picking/simulating a device noise model) >
  #6 (biggest potential compression win, but pulls in an external
  RL+ZX-calculus dependency chain, best as a stretch goal).

NEXT STEPS — REPOSITORY SETUP ROADMAP FOR A DECEMBER JOURNAL SUBMISSION
=====================================================================
Goal: laptop-only compute, ~4 months (from 2026-08-18) to produce
simulation results for a scientific journal. This roadmap is about
repo/engineering setup to make that achievable, not about which
research contribution to pursue (that's a separate, still-open
decision — see the MOO-algorithm and related-work sections above for
candidate angles).

Problems this addresses:
1. No shared code — every notebook redefines its own version of the
   same functions, so nothing guarantees two experiments ran the same
   code (a reproducibility problem reviewers will flag).
2. No experiment runner / structured output — results lived as PNGs
   in out_figs/ and stdout prints; a paper needs tables/figures built
   from many runs across seeds/algorithms/circuit sizes, which needs
   structured, aggregable data.
3. No smoke tests — on a laptop-only budget, multi-hour/overnight
   runs are precious; a silent bug found after an 8-hour run is a full
   day lost.

SCALING — DEFERRED (2026-08-25)
=====================================================================
Between 2026-08-19 and 2026-08-24, significant effort went into making
fidelity computation and the inter-block injection stage tractable
past 8 qubits (replacing the dense-Operator fidelity cutoff with a
SWAP-test/MPS-based estimator, tuning exact-vs-approximate fidelity
thresholds, fixing BLAS thread contention, etc.). That work repeatedly
hit hangs and multi-hour runtimes on genuinely entangled circuit
families (qaoa_maxcut, w_state, qft, hw_efficient_ansatz) at 12+
qubits, and was not fully resolved.

Decision: stop spending time on this for now. The research is moving
forward on the existing 8-qubit dataset (50 runs across all 5 circuit
families, both injection methods, 5 seeds -- see Phase 2 above), which
is complete, fast, and has never hit a performance wall. Scaling past
8 qubits will be revisited later as a separate, dedicated effort.

Note: M1_finale/final_m1_script.py, run_experiment.py, and
aggregate_results.py still carry code from this scaling work (already
committed -- e.g. fidelity_exact_threshold=13 / injection_fidelity_
exact_threshold=12 defaults, the SWAP-test/MPS fidelity backend). Since
those thresholds are all well above 8 qubits, they don't change
behavior at the current 8-qubit scope -- left in place rather than
reverted, but not being built on further for now. run_sweep.py's
CIRCUIT_QUBIT_SIZES was reset to [8] for every circuit (was still
defaulting to 12/16/20q, which would have silently resumed the paused
large-qubit sweep on the next run) -- pass --n-qubits to override for a
one-off run past 8 qubits.

RESEARCH ANGLE CHOSEN AND IMPLEMENTED: SMS-EMOA + operator/hybrid
ablations (2026-08-25)
=====================================================================
Closed the biggest open blocker from Phase 2 above (no research-
contribution angle chosen). Picked, over a noise/crosstalk-aware
objective: **SMS-EMOA as a new per-block optimizer, compared against
NSGA-II (and now-verified NSGA-III), plus two supporting ablations** --
mutation operator combinations (GECCO 2025, arXiv 2504.06413) and a
formalized "pure GA vs. hybrid GA+LAS" comparison (GECCO 2025
companion, arXiv 2504.17561). Chosen specifically because it reuses
existing, already-tested code (compute_hv, the injection stage's
pluggable-strategy pattern) and needs no new dependencies or device-
noise modeling -- lower risk for the laptop-only, ~3.5-month remaining
budget, especially after the scaling work above already lost several
days to unresolved performance walls.

Implemented in M1_finale/final_m1_script.py:
- Fixed a pre-existing bug in optimise_block_nsga2: its per-generation
  loop computed and appended evaluate_run(fits_gen) twice per
  generation (once without P_star, once with), silently doubling
  history_moo's length -- would have broken a fair generation-indexed
  comparison against the new algorithm below. Removed the redundant
  call.
- Added a mutation_scheme param ("point" default == unchanged prior
  behavior, "swap_add", "swap_add_delete") to optimise_block_nsga2,
  via new mut_swap/mut_addition/mut_deletion operators. Chromosomes
  become variable-length under swap_add/swap_add_delete; confirmed
  nothing else assumes fixed length-12 individuals beyond the initial
  population seeding, and DEAP's cxTwoPoint handles unequal-length
  parents safely.
- Added a hybrid_las param (default False) to optimise_block_nsga2:
  when True, runs the LAS local angle search (update_rotation_angles --
  previously dead code, zero call sites anywhere in the file) on the
  GA's winning chromosome before building the final circuit, recording
  las_applied/fidelity_before_las/fidelity_after_las per block.
- New optimise_block_smsemoa function, same chromosome
  encoding/objectives/DEAP creator-guard pattern as optimise_block_nsga2
  (confirmed safe to reuse creator.FitnessMulti/Individual directly --
  same 3 objectives, same maximize/minimize weights). Parent selection
  is binary tournament by Pareto rank (rank via tools.sortNondominated,
  id()-keyed per generation) instead of NSGA-II's crowding-distance
  tournament. Environmental selection stacks whole Pareto fronts while
  they fit pop_size, then for the boundary front iteratively removes
  the individual whose removal loses the LEAST hypervolume (via the
  existing compute_hv/normalize_objectives, same minimize-conversion
  evaluate_run already uses) until back to pop_size -- hand-rolled
  inside the existing DEAP loop rather than pymoo's own SMSEMOA
  algorithm class, to keep one GA framework in the codebase (deliberate
  choice, confirmed with the user; accepted some performance risk in
  exchange). This is a generational adaptation of SMS-EMOA (batches
  offspring per generation, matching evaluate_population's joblib
  parallelism) rather than the textbook's steady-state (mu+1) loop.
  Supports the same mutation_scheme/hybrid_las params.
- optimise_circuit_pipeline gained block_algorithm ("nsga2"/"smsemoa"),
  mutation_scheme, and hybrid_las params, dispatched at the per-block
  call site exactly mirroring the existing injection_method if/elif/
  else pattern. All three are echoed into the returned meta dict
  (analogous to injection_path_used) so metrics.json is self-
  describing.
- Wired through run_experiment.py (--block-algorithm/--mutation-scheme/
  --hybrid-las CLI flags), run_sweep.py (new BLOCK_ALGORITHMS/
  MUTATION_SCHEMES/HYBRID_LAS_OPTIONS axes, defaulting to single-value
  lists so a plain `python run_sweep.py` run is unchanged; run_id_for
  extended to encode all three, avoiding stale-run collisions), and
  aggregate_results.py (3 new CONFIG_FIELDS columns, plus
  n_blocks_hybrid_las_applied/mean_fidelity_before_las/
  mean_fidelity_after_las aggregated from the per-block LAS records).
- tests/test_pipeline_smoke.py: added a 5-case parametrized test
  (smsemoa, each mutation_scheme, hybrid_las, and one combined case).
  Full suite (11 tests) passes.
- Verified end-to-end: a manual run_experiment.py run with
  --block-algorithm smsemoa --mutation-scheme swap_add_delete
  --hybrid-las produced a valid metrics.json with all new fields

Sweep (a) — algorithm comparison — RUN (2026-08-25): 50/50 runs
succeeded (`python run_sweep.py --injection-methods stochastic
--block-algorithms nsga2 smsemoa`), aggregated into
runs/results_master.csv (now 110 rows total alongside the pre-existing
61-run 8q baseline). Mean over all 5 circuits x 5 seeds:

  block_algorithm  fidelity_final  depth_after  cost_after  mean_hv  mean_spread  mean_spacing  total_n_pareto  wall_clock_s
  nsga2                    0.1491        16.04       82.12   0.0520       1.4360        0.0805          121.84       52.41
  smsemoa                  0.1230        15.20       78.24   0.0596       1.6326        0.0870          171.72       50.95

NSGA-II wins on final (best-individual) fidelity in every circuit
family, 16/25 seed-runs overall vs. smsemoa's 9/25 (per-circuit: 3-4
wins out of 5 seeds each, no ties) -- a consistent, not noisy, result.
But SMS-EMOA produces a larger, more diverse Pareto front per run
(total_n_pareto 172 vs 122; mean_hv 0.060 vs 0.052) and slightly lower
depth/cost, at essentially the same wall-clock cost (51s vs 52s mean --
the earlier single-block timing check's finding, that the hand-rolled
hypervolume trim isn't a performance blocker, holds at the full
5-circuit/8-qubit scale too).

Interpretation: at this problem's current fidelity regime (raw
fidelities well below the 0.9999 threshold, same regime Phase 2 already
noted for the injection-method finding), SMS-EMOA's hypervolume-driven
selection trades some peak fidelity for front diversity/coverage --
consistent with the general MOO literature (SMS-EMOA optimizes the set
as a whole via the hypervolume indicator, not the single best point on
one objective). This is itself a legitimate, citable comparison result
("hypervolume-driven selection improves front diversity/hv at a modest
cost to peak fidelity, no wall-clock cost") rather than a clear win for
either algorithm -- worth keeping both in the paper as complementary,
not picking one as "the" method going into sweeps (b)/(c).

Sweep (b) — mutation-scheme ablation — RUN (2026-08-25): 50/50 new runs
succeeded (`python run_sweep.py --injection-methods stochastic
--block-algorithms nsga2 --mutation-schemes point swap_add
swap_add_delete`; 25 of the 75-config grid were already done from
sweep (a)'s point/nsga2 baseline and skipped). Aggregated into
runs/results_master.csv (160 rows total). Mean over all 5 circuits x 5
seeds, block_algorithm=nsga2, hybrid_las=False:

  mutation_scheme   fidelity_final  depth_after  cost_after  mean_hv  mean_spread  mean_spacing  total_n_pareto  wall_clock_s
  point                     0.1491        16.04       82.12   0.0520       1.4360        0.0805          121.84       52.41
  swap_add                  0.1140        16.96       89.64   0.4659       1.0170        0.0837           94.96       56.19
  swap_add_delete           0.1293        15.24       80.52   0.0438       1.4281        0.1004          100.36       53.44

Win counts on fidelity_final (25 circuit x seed combos, argmax across
the 3 schemes): point 12, swap_add 8, swap_add_delete 5.

Findings, checked against the GECCO 2025 source (arXiv 2504.06413)
this ablation was designed to test:
- swap_add_delete beats swap_add on BOTH fidelity (0.1293 vs 0.1140)
  and depth/cost (15.24/80.52 vs 16.96/89.64) here -- consistent with
  the paper's claim that adding deletion gives "a better fidelity/depth
  balance" than swap+addition alone (addition-without-deletion lets
  chromosomes grow unchecked; cost_after 89.64 is the highest of the
  three, confirming that bloat).
- Neither swap-based scheme beats the original point-mutation operator
  on this codebase's problem/representation -- point has the best mean
  fidelity AND best win count of all three. The paper's comparison was
  between the two swap-based variants only, not against a plain
  single-gene-replace baseline, so this isn't a contradiction of it,
  but it does mean the practical takeaway for this pipeline is "keep
  point mutation as the default," with the swap-based schemes reported
  as an ablation showing the addition/deletion trade-off rather than as
  an improvement to adopt.
- Caveat on mean_hv: swap_add's 0.4659 vs the other two schemes' ~0.05
  is NOT a straightforwardly comparable "8x better front quality" --
  compute_hv/evaluate_run normalize each run's own population to its
  own per-run min/max before computing hypervolume, so a scheme whose
  chromosomes bloat more (swap_add's cost_after is the highest here)
  stretches its own objective ranges and can inflate the normalized HV
  number without the front being more genuinely useful. Flagging this
  now so it isn't mistakenly reported as a clean win in the paper --
  any cross-scheme HV comparison would need a shared (not per-run)
  normalization/reference point to be trustworthy.
