=====================================================================
PROJECT OVERVIEW
=====================================================================
Academic research project (French PFE — end-of-studies project) on
optimizing quantum circuits with genetic algorithms. Goal: take a
target quantum circuit (or unitary), partition it, and evolve a
cheaper/shallower circuit that still reproduces the target's behavior
with high fidelity.

Stack: Qiskit (circuit simulation) + DEAP (evolutionary computation,
NSGA-II / NSGA-III style multi-objective optimization).

The codebase is a research sandbox, not a packaged library: a
progression of standalone Jupyter notebooks and scripts, each an
iteration of the same core pipeline (mono-objective -> multi-objective
-> block-decomposed/scalable). No shared package, no test suite, no
build step.

=====================================================================
CORE PIPELINE (M1_finale/final_m1_script.py) — reference implementation
=====================================================================
Entry point: optimise_circuit_pipeline(...)

1. Partitioning
   - build_interaction_graph: qubit-interaction graph weighted by
     2-qubit gate count.
   - louvain_partition: Louvain community detection to split qubits
     into blocks.
   - multilevel_partition: Metis/Kernighan-Lin recursive alternative
     for bounding block size.
   - extract_interblock_gates: captures gates crossing block
     boundaries for later reinjection.

2. Sub-circuit extraction / recomposition
   - extract_subcircuit: pulls a self-contained, locally-reindexed
     circuit per block.
   - recompose_from_blocks: stitches optimized block circuits back
     into a global circuit in original gate order, preserving
     inter-block gates unchanged.

3. Fidelity metric
   - compute_fidelity: operator-overlap fidelity
     |Tr(U_circ . U_target^dagger)| / 2^n.
   - Short-circuits to 1.0 above 15 qubits to avoid dense-matrix
     blowup — this cap is why the pipeline is only exercised on
     small/weakly-connected circuits despite claiming to scale.

4. Intra-block optimization
   - optimise_block_nsga2: DEAP NSGA-II per block, three objectives
     (maximize fidelity, minimize transpiled depth, minimize
     chromosome-length cost).
   - update_rotation_angles: finite-difference local search ("LAS")
     nudging rotation angles after the genetic search converges.

5. Inter-block gate injection (re-adds cross-block entanglement lost
   during block-local optimization)
   - sa_injection: simulated annealing over an energy combining gate
     count, depth, crosstalk, fidelity penalty.
   - stochastic_injection: random trial-and-keep-if-fidelity-improves.
   - fidelity_driven_injection: simpler greedy variant, used as a
     complementary final pass.

6. Compression
   - Hand-rolled passes: cancel_inverse_gates, merge_rotations,
     remove_negligible_rotations (composed in compress_custom).
   - Standard Qiskit PassManager pass (qiskit_opt_pass):
     Optimize1qGates + CommutativeCancellation.

7. Multi-objective quality indicators
   - evaluate_run / compute_hv / spread_delta / compute_spacing /
     compute_epsilon: hypervolume, spread, spacing, epsilon indicator,
     and IGD when a reference Pareto front (P_star) is supplied.
   - Tracked across generations, not just best-fitness.
   - export_all_indicators / plot_moo_history / save_plot /
     plot_convergence / plot_pareto / plot_3d_clusters write PNGs to
     out_figs/ (created on demand).

Later stages depend on earlier ones' output shape (block list,
per-block optimized circuit, kept-injection list) — check
optimise_circuit_pipeline's call sequence before changing an output
type.

Also present: random_weakly_connected_circuit — generates synthetic
test circuits (used by the 30-qubit and 64-qubit runnable examples).

=====================================================================
CONVENTIONS SPECIFIC TO THIS CODEBASE
=====================================================================
- Chromosome encoding: individuals are Python lists of gene tuples
  (gate_name, target_qubit, ctrl_qubit_or_None, angle_or_None). Any
  new gate type added to a gate_pool needs matching branches in every
  build/build_fn closure that turns chromosomes into QuantumCircuits
  (these closures are redefined locally inside each optimisation
  function rather than shared).
- DEAP creator classes (creator.FitnessMulti, creator.Individual) are
  registered guarded by hasattr(creator, ...) checks since DEAP raises
  on re-registration — preserve this guard across notebook re-runs.
- Figures are a primary output, not incidental logging — stdout
  progress prints use emoji status markers (checkmark/cross/money/
  pin-style icons). Keep this pattern when extending a pipeline stage.
- Comments, docstrings, print messages, plot labels, and markdown
  prose are English throughout (originally French, translated in
  full). The two thesis PDFs at the repo root remain in French
  (academic writeups, not code).
- Most heavy computation (chromosome fitness evaluation) is
  parallelized via joblib.Parallel(n_jobs=...) — eval_ind-style
  functions must stay picklable for multiprocessing.

NEXT STEPS — CANDIDATE MOO ALGORITHMS TO ADD
=====================================================================
Beyond NSGA-II/NSGA-III, the following multi-objective algorithms
would fit naturally into the existing per-block optimization slot
(currently optimise_block_nsga2 in M1_finale/final_m1_script.py) and
could be added as interchangeable strategies, similar to how
sa_injection / stochastic_injection / fidelity_driven_injection are
already interchangeable for the injection stage.

1. SMS-EMOA (S-Metric Selection EMOA)
   - Hypervolume-indicator-driven selection instead of crowding
     distance. Directly reuses the project's existing compute_hv
     function as the selection criterion rather than just as a
     post-hoc reporting metric — tightest synergy with code already
     in the repo.
   - Tends to produce better-distributed, higher-quality fronts than
     NSGA-II for 2-3 objectives (fidelity, depth, cost), at higher
     per-generation cost (hypervolume contribution calculation).

2. IBEA (Indicator-Based Evolutionary Algorithm)
   - Generalizes SMS-EMOA to arbitrary indicators; could plug in
     compute_epsilon (already implemented) as the driving indicator
     instead of hypervolume. Good candidate for comparing indicator
     choices against each other using the project's own
     evaluate_run/export_all_indicators reporting.

3. MOEA/D (Decomposition-based MOEA)
   - Decomposes the 3-objective problem (fidelity, depth, cost) into
     scalar subproblems via weight vectors (Tchebycheff or weighted
     sum), each solved cooperatively with neighbor information sharing.
   - pymoo (already a project dependency per requirements notes) ships
     a ready MOEA/D implementation — lowest implementation cost of
     this list if built on pymoo rather than hand-rolled in DEAP.
   - Conceptually maps well onto the block-partition architecture:
     each qubit block could own a distinct region of weight-vector
     space rather than all blocks running identical NSGA-II.

4. SPEA2 (Strength Pareto EA 2)
   - Classic alternative fitness assignment (strength + density via
     k-th nearest neighbor) with an external archive of fixed size.
   - Useful as a baseline comparison against NSGA-II on the same
     3-objective problem to see whether NSGA-II's crowding distance
     is actually the best diversity mechanism for this circuit search
     space, or just the default choice inherited from earlier
     iterations of the project.

5. Multi-Objective Simulated Annealing (MOSA)
   - The project already has single-objective SA for inter-block
     injection (sa_injection, energy = weighted combination of gate
     count, depth, crosstalk, fidelity penalty). A genuinely
     multi-objective SA (Pareto-dominance-based acceptance criterion,
     archive of non-dominated states) could replace that weighted-sum
     energy function and produce a full injection-stage Pareto front
     instead of a single injected solution.
   - Lower implementation lift than the above since it extends
     existing SA machinery (_sa_energy, _sa_rand_move, _sa_generate_pool)
     rather than introducing a new population-based framework.

6. MOPSO (Multi-Objective Particle Swarm Optimization)
   - Different metaheuristic paradigm (swarm, not GA) — worth
     including as a diversity-of-method comparison point in the
     thesis, since all current algorithms (NSGA-II/III, SA variants)
     are either GA- or SA-based.
   - Chromosome encoding (gate_name, target_qubit, ctrl_qubit, angle)
     would need a continuous-relaxation or discrete-PSO adaptation
     before particles can be applied to gate sequences — higher
     implementation cost than the others on this list.

Suggested priority order given existing code reuse:
  MOSA (extends sa_injection) > SMS-EMOA (reuses compute_hv) >
  IBEA (reuses compute_epsilon) > MOEA/D (via pymoo) > SPEA2 > MOPSO.

NEXT STEPS — IMPROVEMENTS FROM RELATED WORK (web research, 2026-08-18)
=====================================================================
Grounded in recent (2024-2026) literature on GA/MOO quantum circuit
optimization, partitioning, and alternatives. Each item names why it
applies to this specific codebase, not just in general.

1. Hyperedge-aware partitioning instead of pairwise Louvain clustering
   - build_interaction_graph/louvain_partition collapse multi-qubit
     gates to pairwise edges and fix block structure via modularity.
   - A 2025 dynamic hypergraph partitioning approach models gates as
     hyperedges (qubit x time nodes) and sweeps block-count K with
     METIS instead of assuming modularity picks the right K.
   - Source: arXiv 2506.09963

2. Cheaper fidelity proxy to replace the hard 15-qubit cutoff
   [DONE 2026-08-19 -- see "FIDELITY-COMPUTATION SCALING FIX" below.
   Took a different route than this specific paper's projection-based/
   NSGA-II-folded approach -- ported and fixed nex_formula's existing
   SWAP-test estimator instead, switched to matrix_product_state
   simulation. Net effect is the same: the hard cutoff is gone.]
   - compute_fidelity short-circuits to 1.0 above 15 qubits — a
     "Scalable Multi-Objective Genetic Algorithm for Quantum Circuit
     Optimization" paper targets this exact bottleneck via a
     projection-based approximation + structure-aware local metric
     folded directly into NSGA-II, avoiding full dense-unitary builds.
   - Source: nature.com/articles/s41598-026-47674-5 (worth reading in
     full; preprint mirror was paywalled/403 at research time)

3. Classical-shadow / tensor-network fidelity estimation for scale
   [DONE 2026-08-19 -- see "FIDELITY-COMPUTATION SCALING FIX" below.
   Not classical-shadow tomography specifically, but the same
   tensor-network idea: matrix_product_state simulation of a SWAP-test
   circuit, which is what actually made this tractable past 15 qubits
   for this project's weakly-connected circuits.]
   - Tensor-network-backed classical shadow tomography gives
     sample-efficient fidelity/property estimation without building
     the full 2^n x 2^n operator — would let the pipeline's scaling
     claims actually be tested past 15 qubits instead of stubbed out.
   - Source: arXiv 2209.02093

4. Benchmark mutation operator combinations explicitly
   - GECCO 2025 work found "swap+addition" maximizes fidelity but
     grows depth, while "swap+addition+delete" gives a better
     fidelity/depth balance.
   - optimise_block_nsga2's mutation operators are currently a fixed,
     one-off choice — this gives a citable, testable ablation to run
     per-block and report on.
   - Source: arXiv 2504.06413

5. Formalize the hybrid GA + parameter-refinement split as a named,
   compared variant
   - A companion GECCO 2025 paper separates "hybrid" (GA + rotation-
     parameter subroutine) from "pure" (mutation/crossover only)
     variants, and tests both "build from scratch" and "refine
     existing circuit" starting points.
   - This project already has an ad-hoc version of the hybrid idea
     (update_rotation_angles/LAS after NSGA-II) but has never
     formalized it as a variant to compare against pure-GA — an easy
     controlled experiment to add.
   - Source: arXiv 2504.17561

6. RL + ZX-calculus as a compression-stage alternative
   - An RL agent (PPO + GNN) applying ZX-diagram rewrite rules scales
     to 80 qubits / thousands of gates and beats hand-coded ZX
     simplification strategies; a PyZX-based Qiskit transpiler pass
     exists for integration.
   - compress_custom's hand-rolled inverse-cancellation/rotation-
     merging passes are exactly the category of hand-coded rule this
     method outperforms — could be swapped in, or run as an
     additional final compression pass.
   - Source: arXiv 2312.11597 (Quantum, 2025)

7. Add a noise/crosstalk-aware objective, not just math fidelity
   - Frameworks like CQC (crosstalk-aware compilation) and CCMap
     (coupler-aligned, noise-aware modular compilation; +21.9%
     fidelity / -58.6% compile cost vs baselines in their reported
     results) fold real device error rates and crosstalk into the
     cost function rather than treating fidelity as pure unitary
     overlap.
   - Directly closes a gap this project's own docs already note (no
     noise model, no coupling-map awareness) — could become a 4th
     NSGA-II objective, or a term in the SA injection energy function
     (_sa_energy already has a crosstalk term placeholder to extend).
   - Sources: arXiv 2207.05751, arXiv 2505.09036

8. Noise-weighted partition cuts
   - DisMap/FitCut-style distributed compilation weights partition
     boundaries by qubit error rate/topology, not just gate-crossing
     count, when deciding where to cut.
   - extract_interblock_gates/partitioning currently only minimizes
     cross-block gate count — adding a hardware-error term would make
     block boundaries reflect real device quality, complementing #7.

Suggested priority given effort vs payoff for the thesis:
  #4 and #5 (cheap, purely experimental/ablation, no new deps) >
  #1 (partitioning quality, moderate effort) >
  #2/#3 (removes the 15-qubit ceiling, the project's most-cited
  limitation, but higher implementation effort) >
  #7/#8 (adds a genuinely new evaluation dimension — hardware realism
  — but requires picking/simulating a device noise model) >
  #6 (biggest potential compression win, but pulls in an external
  RL+ZX-calculus dependency chain, best as a stretch goal).

NEXT STEPS — REPOSITORY SETUP ROADMAP FOR A DECEMBER JOURNAL SUBMISSION
=====================================================================
Goal: laptop-only compute, ~4 months (from 2026-08-18) to produce
simulation results for a scientific journal. This roadmap is about
repo/engineering setup to make that achievable, not about which
research contribution to pursue (that's a separate, still-open
decision — see the MOO-algorithm and related-work sections above for
candidate angles).

Problems this addresses:
1. No shared code — every notebook redefines its own version of the
   same functions, so nothing guarantees two experiments ran the same
   code (a reproducibility problem reviewers will flag).
2. No experiment runner / structured output — results lived as PNGs
   in out_figs/ and stdout prints; a paper needs tables/figures built
   from many runs across seeds/algorithms/circuit sizes, which needs
   structured, aggregable data.
3. No smoke tests — on a laptop-only budget, multi-hour/overnight
   runs are precious; a silent bug found after an 8-hour run is a full
   day lost.

FIDELITY-COMPUTATION SCALING FIX (2026-08-19)
=====================================================================
Addresses the blocker Phase 2's benchmark sweep hit (a 12-qubit
weak_random run still running after 1h45m, killed rather than let
finish) and delivers related-work item #3 above (tensor-network-backed
fidelity estimation past the 15-qubit cutoff) -- turned out to overlap
heavily with item #2 as well, since the same fix removes the hard
cutoff entirely rather than just extending it.

Root cause: compute_fidelity computes a dense Operator trace fidelity,
and injection-stage functions call it on the FULL recomposed circuit
hundreds to thousands of times per run -- _sa_energy once per SA
iteration (default sa_iters=3000), fidelity_driven_injection twice per
trial (default max_trials=300 -> 600 calls), plus stochastic_injection
and optimise_circuit_pipeline's own summary checks. Cost scales with
the 2^n x 2^n matrix dimension: 8 -> 12 qubits is a 16x bigger matrix
and a much-larger-than-16x runtime increase per call.

Final_test/nex_formula already had an approximate-fidelity estimator
(safe_fidelity_between_circuits: exact below a qubit threshold,
Monte-Carlo SWAP-test above it) sitting unused for exactly this.
Before integrating it, ported it standalone and validated it directly
-- found it silently BROKEN: _swap_test_circuit builds
QuantumCircuit(total, 1) (an implicit classical register) and then
adds a SECOND ClassicalRegister for the actual measurement, so
get_counts() returns two-register keys like '0 0', but the code checks
counts.get('0', ...), which never matches -- every estimate silently
returned 0.0, including for identical circuits (which must be ~1.0).
Fixed (single classical register, no implicit extra bit) and confirmed
against exact fidelity on test cases before trusting it further.

Also discovered mid-validation, changing the plan materially: the
SWAP-test circuit itself has 2n+1 qubits, so Aer's DEFAULT simulation
method is exponential in THAT, not just in n -- outright rejected
above 31 total qubits (CircuitTooWideForTarget) and would be
infeasible around n=15 even where it "works". Tested
AerSimulator(method="matrix_product_state") directly against a
20-qubit weakly-connected target (41-qubit SWAP-test circuit): no
qubit-count-driven slowdown at all (n=8/12/16 all ~0.06-0.08s at 512
shots) -- cost is dominated almost entirely by shots (linear:
64->0.4s, 512->2.4s, 2048->9.6s per sample), not qubit count, because
this project's circuits are weakly-connected/low-entanglement by
design. MPS, not the default method, is what actually makes this scale
for the circuits this pipeline targets.

Implemented in M1_finale/final_m1_script.py:
- safe_fidelity_between_circuits(qc_a, qc_b, exact_threshold=10,
  samples=8, shots=128, seed=0) plus helpers (_rand_product_prep,
  _swap_test_circuit, approximate_gate_fidelity_swap_mc), ported from
  nex_formula with the classical-register bug fixed and hardcoded to
  AerSimulator(method="matrix_product_state") -- never the default
  method. Defaults lower than nex_formula's (threshold 12->10, samples
  32->8, shots 2048->128) based on the measured ~0.0046s/shot cost.
- optimise_circuit_pipeline: dropped the "if n<=15: build dense Operator
  else: dummy identity" special case entirely -- qc_orig (the actual
  circuit) is always cheap to keep regardless of size, which is what
  the new function needs instead of a prebuilt matrix. All 5
  full-circuit fidelity checks (fid_rebuilt, fid_rebuilt1, fid_inj,
  fid_i, fid_final) now go through safe_fidelity_between_circuits
  against qc_orig directly.
- sa_injection/_sa_energy, stochastic_injection,
  fidelity_driven_injection: switched from precomputed target-unitary
  matrices to safe_fidelity_between_circuits. Per-block GA
  (optimise_block_nsga2, update_rotation_angles) and other per-block
  compute_fidelity call sites are UNCHANGED -- blocks stay at or under
  max_block_size=5, well within any reasonable exact_threshold, so the
  existing exact-matrix path there was already correct and efficient.
- fidelity_driven_injection also stopped recomputing the unchanged
  side's fidelity every trial (candidate_qc only changes on
  acceptance) -- halves the fidelity calls in that loop, a direct,
  in-scope efficiency win for the exact problem being solved.
- run_experiment.py: new --fidelity-exact-threshold (default 10),
  --fidelity-swap-samples (default 8), --fidelity-swap-shots (default
  128) CLI flags.
- meta["fidelity_backend"] ("exact" or "swap_test_mc") plus the
  threshold/samples/shots actually used, now recorded per run and
  surfaced in aggregate_results.py's master table -- approximate runs
  carry sampling noise and shouldn't be treated as bit-comparable to
  exact ones without knowing which path produced them.
- New tests/test_fidelity_estimator.py: a permanent regression guard
  for the exact bug found (identical circuits must estimate ~1.0, not
  silently 0.0), plus an exact-vs-approximate agreement check.
  tests/test_pipeline_smoke.py extended with a case that forces the
  approximate path on the existing tiny circuit (fidelity_exact_threshold
  below its qubit count) rather than needing a slower real 12+ qubit
  case for the same coverage.

Verified: full test suite passes (10/10). The exact 12-qubit
weak_random config that motivated this (sa injection, previously
1h45m+ before being killed) now completes in 4m32s with tiny GA
settings, metrics.json correctly showing fidelity_backend:
"swap_test_mc". An 8-qubit run confirms the exact path is unchanged

Disclosed, not solved in this pass (deliberately, to avoid hidden

INJECTION-STAGE FIDELITY COST FIX (2026-08-21)
=====================================================================
Follow-up to the FIDELITY-COMPUTATION SCALING FIX above. That fix removed
the hard 15-qubit cutoff, but a sweep config (weak_random, 20 qubits,
stochastic injection) still ran for over an hour without completing --
this section covers root-causing and mitigating that.

Root cause: safe_fidelity_between_circuits' Monte-Carlo SWAP-test estimator
was validated (in the fix above) against near-identical, low-entanglement
circuit pairs and found cheap and roughly qubit-count-independent there.
But the injection stage's entire job is to test candidates that differ from
the base circuit by one newly-added CROSS-BLOCK entangling gate (cx/cz/rzz
spanning two different partition blocks) -- exactly the kind of pair the
earlier validation never tested. The SWAP-test's cswap ladder has to
represent that genuine entanglement, which is dramatically more expensive
for the matrix_product_state simulator than a near-identical pair.
Measured directly on the actual stalled circuit (20-qubit weak_random,
comparing the original circuit against a candidate with one extra
cross-block cx): a single fidelity call at the pipeline's general defaults
(samples=8, shots=128) exceeded 900s (killed after 15+ min, still running)
-- versus 11.5s for a same-circuit comparison using the same settings. Every
one of the ~400 sequential trials in stochastic_injection (100) and the
always-on fidelity_driven_injection greedy pass (300) hits this expensive
case, which is why every large-qubit sweep config stalled regardless of the
thread-oversubscription fix below.

Ruled out first: this is not the old dense-Operator bug (no call path
builds a dense Operator above fidelity_exact_threshold=10; verified by
reading every Operator(...)/compute_fidelity call site), and not a hang --
confirmed via before/after CPU-time deltas that the process was genuinely
computing throughout, not deadlocked.

Fix: added separate, much cheaper fidelity settings used ONLY inside the
injection stage's per-trial loop (sa_injection/_sa_energy,
stochastic_injection, fidelity_driven_injection), distinct from the
pipeline's general fidelity_samples/fidelity_shots which remain at their
existing values for the pipeline's own reporting-level checks (fid_rebuilt,
fid_rebuilt1, fid_inj, fid_i, fid_final -- these run only a handful of times
per pipeline call, not hundreds, so their accuracy isn't the bottleneck).
New parameters on optimise_circuit_pipeline: injection_fidelity_samples
(default 2) and injection_fidelity_shots (default 16), threaded into
run_experiment.py as --injection-fidelity-samples/--injection-fidelity-shots
and recorded in metrics.json.

Benchmarked directly on the same hard pair (the actual stalled 20-qubit
config's circuit + one extra cross-block gate) before settling on defaults:
  - samples=8, shots=128 (old general default): >900s/call, projects to
    hours+ for 400 trials -- this is what stalled.
  - samples=2, shots=16 (new default): 40.5s/call, ~270 min (4.5h) for 400
    trials -- a real ~22x+ speedup, cost still scales roughly linearly with
    total shots (not a large fixed floor), but still slow at this qubit
    count/circuit.
  - samples=1, shots=8 (most aggressive floor tried): 11.65s/call, ~78 min
    for 400 trials -- faster, but 8 total measurement shots makes the
    fidelity estimate driving each greedy accept/reject decision close to
    meaningless statistical noise.
Conclusion: reducing samples/shots alone cannot bring this into a fast
regime without degrading the injection stage's actual accept/reject
signal into noise -- kept the samples=2/shots=16 default as a genuine,
measured improvement (not a full solution), and flagged for the user that
a further fix (e.g. restricting the SWAP-test to the affected qubits/blocks
rather than the full circuit) would need to replace tuning these two
knobs further. Not implemented in this pass.

Separately (found and fixed in the same investigation, not what caused
the multi-hour stalls but a real inefficiency): the injection stage's
sequential per-trial loop was running with no BLAS thread cap, so every
small linear-algebra call (compress_custom, qiskit_opt_pass, the fidelity
check itself) independently spun up a thread pool sized to every core the
process could see -- 94 threads observed on one process, with wall-clock
CPU time running at ~16x realtime due to contention, not genuine
parallelism (actual parallelism for this pipeline comes from joblib's
process-level fan-out in optimise_block_nsga2, not from each individual
matrix op competing for every core). Fixed by capping OMP_NUM_THREADS/
OPENBLAS_NUM_THREADS/MKL_NUM_THREADS/NUMEXPR_NUM_THREADS/
VECLIB_MAXIMUM_THREADS to 1 via os.environ.setdefault(...) at the top of
M1_finale/final_m1_script.py, before numpy/qiskit-aer are imported (these
libraries read the env vars once at init, not per-call). Verified via
threadpoolctl that every thread pool (numpy's OpenBLAS, scipy's,
scikit-learn's, and qiskit-aer's own bundled OpenBLAS) reports
num_threads: 1 after this change; thread count on a live run dropped from
94 to ~22-43, and CPU time began tracking wall-clock 1:1 instead of ~16:1.
This cap is a deliberate, permanent default (not a tunable CLI throttle) --
per instruction, this project's stance is that full process-level
parallelism (joblib's Parallel(-1)) is intentional and hardware-level
thermal safety is not something this software needs to manage; this fix is
about eliminating wasted contention inside a single process, not capping
overall resource usage.

Verified: full pytest smoke suite (10/10) passes with all of the above
applied.

SWAP-TEST FIDELITY BLOWUP ON GENUINELY ENTANGLED CIRCUITS (2026-08-24)
=====================================================================
Discovered while resuming the Phase 2 12/16/20-qubit sweep (the 44 configs
left over from 2026-08-21, see that section's "Not started" note). Before
launching the full remaining batch, timed one real 20-qubit weak_random
config (stochastic injection, real settings g100/p100): 188.8s end-to-end
(partitioning 0.3s, block_optimization 112.6s, injection 64.3s) -- looked
safe, so the remaining 44-config sweep was launched.

It was not safe in general -- only for weak_random. Launched via run_sweep.py
in the background and checked in on periodically:
- All 4 remaining weak_random_20q configs completed, but with far more
  variance than the one timed sample suggested: 149.3s / 1632.7s / 2444.0s /
  5468.4s (2.5 min to 91 min) for otherwise-identical settings, different
  only by seed. Root cause (consistent with the 2026-08-21 section):
  injection-stage cost depends on which specific cross-block gate pair gets
  tested, not just qubit count -- some seeds' partitions happen to produce
  cheap pairs, others expensive ones. Not a new bug, just wider variance
  than one sample revealed.
- The next config (qaoa_maxcut_12q_stochastic_seed0) then hung: still
  running after 110+ minutes with zero new output. Diagnosed live via
  /proc/<pid>/io (wchar/syscw unchanged across a 15s window while CPU stayed
  pegged at ~100%) -- confirmed it was stuck computing inside a single call,
  not slowly progressing through many silent trials. Killed (SIGTERM,
  cleanly; run_sweep.py's per-config subprocess isolation meant the sweep
  itself just logged it as [fail] and moved on, no manual sweep restart
  needed). The very next config, qaoa_maxcut_12q_stochastic_seed1, hit the
  identical signature (same zero-I/O-while-100%-CPU fingerprint, ~51 min in)
  -- ruling out a one-off fluke tied to seed0's specific random circuit and
  pointing at something systemic to the qaoa_maxcut circuit family. Also
  killed.

Root cause, confirmed by direct reproduction (not just inferred from the
hang): built a synthetic candidate circuit shaped like a real post-
stochastic_injection output (a lightly-entangled base plus 6 cross-block
rzz gates, matching the "N gates retained" counts actually seen in the
sweep log) and timed safe_fidelity_between_circuits against a real
qaoa_maxcut_circuit(12, p=2) target:
  - injection_fidelity_samples=2 / shots=16 (the "cheap" defaults added by
    the 2026-08-21 fix specifically to keep the injection-stage per-trial
    loop fast): 242.8s for ONE call -- already ~6x worse than that fix's
    own worst-case benchmark (40.5s, measured only against weak_random
    circuits).
  - fidelity_swap_samples=8 / shots=128 (the general/reporting defaults):
    exceeded a 300s timeout, never returned.
Mechanism: optimise_circuit_pipeline calls safe_fidelity_between_circuits
at the general (expensive) settings five times per run purely for reporting
(fid_rebuilt, fid_rebuilt1, fid_inj, fid_i, fid_final --
M1_finale/final_m1_script.py lines ~1487/1494/1513/1519-ish/final-summary),
on the 2026-08-21 fix's assumption that "a handful of calls" wouldn't matter
even at the pricier settings. That held for weak_random because its target
circuit is weakly entangled by construction. qaoa_maxcut's target is a real
QAOA circuit (rzz layers across a ring+chord graph, genuinely entangled) --
the MPS-backed SWAP-test's cost blows up on genuinely entangled circuit
PAIRS (candidate structure AND target structure both matter), independent
of samples/shots. Lowering shots further would not reliably fix this: the
already-"cheap" injection settings still took 4 minutes in the repro.

Practical implication: this is not a weak_random-specific or seed0-specific
fluke. w_state, qft, and hw_efficient_ansatz are also "genuinely entangled"
circuit families (not weakly-connected like weak_random) and are live
candidates to hit the same wall at 12+ qubits -- untested as of this entry
since the sweep was paused before reaching them.

Not fixed in this pass -- paused the sweep instead of continuing to
individually discover and kill hangs. Two follow-ups identified, not done:
1. Pragmatic/immediate: run_sweep.py has no per-config watchdog timeout --
   a hung config currently requires manual detection (via /proc/<pid>/io,
   as done here) and a manual kill before the sweep's own crash-isolation
   (subprocess-per-config, [fail]-and-continue) can take over. Adding an
   automatic timeout would let a sweep run unattended through configs like
   this instead of stalling indefinitely.
2. Real fix, larger: the underlying gap is that safe_fidelity_between_
   circuits' MPS SWAP-test is not a robust proxy once either circuit in the
   pair is genuinely entangled, and the pipeline's 5 general-settings calls
   were never gated by the same cost awareness as the injection-loop calls.
   Two independent angles worth considering: (a) restrict the SWAP-test to
   the affected qubits/blocks instead of the full circuit -- explicitly
   flagged as unimplemented follow-up in the 2026-08-21 section already;
   (b) qc_orig is only 12 qubits here, well within compute_fidelity's dense-
   Operator range -- the approximate path is only being used because
   fidelity_exact_threshold defaults to 10, not because exact computation is
   actually intractable at this size. Revisiting the threshold itself (or
   making the general/reporting calls prefer exact fidelity whenever both
   circuits are small enough) may be cheaper than fixing the approximation.

Sweep state: paused at the user's request at 60/100 configs done (56 from
2026-08-19/21 plus the 4 weak_random_20q configs from this session).
